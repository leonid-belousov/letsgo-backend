# Дизайн: изолированные mock-сценарии для Let'sGo

**Статус:** предложенный дизайн, ожидает проверки пользователем. Реализация и план работ ещё не начаты.

## Решение

Сделать каталог типизированных демонстрационных сценариев и доступные только в dev-сборках экраны в web и mobile. Сценарии меняют только локальное состояние демонстрационного экрана: они не вызывают реальные API для недостающих функций, не записывают данные в базу и не меняют поведение обычных экранов. Backend не получает mock endpoints, demo provider или искусственные бизнес-правила.

Каждый экран и объект должен явно показывать:

> MOCK / DEMO — данные и действия ненастоящие; заменить на подтверждённый production-контракт перед боевым запуском.

Предложенные значения (даты, суммы, статусы и переходы) являются иллюстративными, а не решениями продукта.

## Основание и ограничения

- Основной отчёт и `OPEN_DECISIONS.md` перечисляют продуктовые пробелы в правилах турниров, клубных игр, бронирований, платежей и интеграций.
- Правила frontend/mobile требуют считать backend источником состояния и не выдумывать права/бизнес-поведение. Запрошенные fixtures поэтому будут отдельным demo-контуром, не подменой серверных экранов.
- Backend-инструкции запрещают mock services в рабочей логике. В backend останутся только обычные тестовые doubles там, где их требует unit-тест; действующая интеграционная проверка продолжит использовать PostgreSQL.
- Не добавлять MSW: для локальных экранов без сетевых запросов перехват API не нужен. Официальная документация MSW описывает React Native integration, но помечает её использование как рискованное; отдельная тестовая/демо-сеть добавила бы лишнюю точку обслуживания.

## Охват сценариев

В демо-каталог включать сценарии из открытых спецификационных пробелов:

1. **Турнир:** конфигурация сроков/дополнительных услуг/платёжных переключателей как пример; результат ожидает подтверждения; предварительный вариант разрешения равенства.
2. **Командная игра:** готовность клубов; условное назначение менеджера результата; пример мини-таблицы.
3. **Бронирование:** бронь с условием минимального числа игроков и гарантированная бронь; внешняя аренда с примером суммы/получения наличных; предпросмотр закрытия площадки с демонстрационным возвратом.
4. **Внешние интеграции:** демонстрационные состояния provider sign-in, push и возврата из внешнего редактора/социального приложения. Не создавать OAuth-токены, реальные push-сообщения, внешние ссылки публикации или записи о медиа.
5. **Поведение ошибок:** демонстрационные состояния «недоступно», «ожидает ответа» и «отклонено» для сценариев, где отсутствие provider/backend сейчас блокирует настоящий поток.

Каждый scenario ID сопоставляется пункту отчёта или acceptance matrix. Имена, контакты и идентификаторы — синтетические; персональные данные из рабочих баз, документов и скриншотов запрещены. Device QA (TalkBack, частичные разрешения фото, процесс смерти, производительность, iOS runtime) нельзя закрыть mock-данными и остаётся отдельной физической/эмуляторной проверкой.

## Данные и граница API

У каждого demo-сценария есть стабильный ID, домен, `mockOnly: true`, ссылка на источник требования, список условных предположений, набор синтетических данных, доступные локальные demo-переходы и описание того, чем заменить сценарий после появления утверждённого API-контракта.

Для текущих API разрешены только примеры, совместимые с сгенерированными OpenAPI-типами. Поля, которых ещё нет в API, принадлежат отдельной модели demo-view; их нельзя добавлять в generated schema, выдавать за backend DTO или передавать через реальный `api` client. Неизвестные продуктовые решения показываются как варианты/placeholder, не как автоматически выбранное правило.

Web и mobile находятся в отдельных npm-проектах с разными runtime/bundler-конфигурациями. Чтобы не добавлять межпроектный пакет и настройки Metro/Vite ради фикстур, каждый клиент получает небольшие локальные типизированные данные с одинаковыми scenario IDs и единым root-документом-каталогом; проверки должны выявлять расхождение списка IDs.

## Доступ и безопасность

- Web: точка входа и динамическая загрузка demo-screen допустимы только за `import.meta.env.DEV`.
- Mobile: точка входа допустима только за `__DEV__`; не добавлять публичный `EXPO_PUBLIC_*` переключатель моков и не полагаться на секретность переменных клиента.
- Демонстрационные действия обновляют только локальное состояние экрана; не используют auth/session, grants/capabilities, payment/booking mutations, SecureStore или API-клиенты.
- Обычные production routes и API остаются неизменными. Backend никогда не отдаёт demo-данные.
- В release проверяется отсутствие доступной demo-точки входа/исполняемого mock flow. Физическое исключение каждого байта фикстур из bundle не считается доказанным до проверки конкретной конфигурации сборки.

## Критерии приёмки

1. Есть каталог сценариев для каждого согласованного выше домена с уникальными ID и source reference.
2. Любая страница, объект и локальный переход явно остаются помеченными MOCK/DEMO; пометка не исчезает при смене состояния.
3. Клиентские демо-экраны работают без запущенного backend и не вызывают сетевых операций для этих сценариев.
4. Release build не даёт открыть демо-поток; тест проверяет dev-гейт. Demo fixtures не содержат production credentials, токенов, контактов или реальных пользовательских данных.
5. Для значений из открытых продуктовых решений рядом видна пометка, что пример условный и не утверждает финальную политику.
6. Backend OpenAPI, production services, migrations, авторизация и реальные клиентские API-потоки не меняются в рамках mock-демо.
7. Проверки после реализации: typecheck, lint, unit/component tests и production build/export для web и mobile; отдельно подтвердить сетевые вызовы demo-действий отсутствуют. Эмулятор/устройство проверяется только при доступности среды, а mock QA не засчитывается как device QA.

## Перевод из demo в production

Для каждого scenario ID: получить утверждённое продуктовое решение; добавить/изменить backend DTO, endpoint и OpenAPI; регенерировать клиентские типы; заменить demo-view данными реального API и серверными capabilities; реализовать idempotency/permissions/transaction semantics там, где они нужны; добавить интеграционные тесты; удалить локальные mock transitions; затем убрать demo entry point и fixture. Нельзя считать fixture production-ready только потому, что она отображается правдоподобно.

## Исследованные первичные источники

- OpenAPI 3.0.4: media examples SHOULD match the associated schema — <https://spec.openapis.org/oas/v3.0.4.html>.
- MSW React Native guide: отдельная интеграция `@msw/react-native`, с предупреждением использовать на свой риск — <https://mswjs.io/guides/integrations/react-native>.
- Expo environment variables: `EXPO_PUBLIC_*` вшиваются в клиентский bundle; секреты нельзя хранить в таких переменных — <https://docs.expo.dev/guides/environment-variables/>.
- NestJS custom providers/testing: `useValue`/`overrideProvider` подходят для подмен в тестах — <https://docs.nestjs.com/fundamentals/testing>.

## Самопроверка дизайна

- Не добавляется mock API, mock backend service, MSW или дополнительная runtime-зависимость.
- Никакой незакрытый пункт `OPEN_DECISIONS.md` не превращается в рабочее правило.
- Device-specific/OS-specific приёмку не подменяем демо-экраном.
- Чётко отделены сгенерированные реальные API-типы от mock-only view models.
- Перед реализацией пользователю нужно просмотреть этот дизайн; после одобрения — отдельный implementation plan и согласование способа исполнения.
